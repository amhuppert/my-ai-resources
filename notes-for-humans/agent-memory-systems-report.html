The memory layer

A source-inspected map of how AI agents remember: from context windows and flat files to temporal graphs, governed knowledge bases, procedural skill libraries, and learned memory policies.

35 HN comments reviewed 15 repositories inspected 34 source groups cited Coding-agent focus
01

Executive verdict

Memory is governed state, not a bigger prompt

The field is converging on selective, typed, provenance-bearing memory. It has not converged on one storage engine—and the evidence says it should not.

The best current design is a layered one: keep authoritative project truth in versioned files; keep volatile work in the active context and checkpoint; promote only reusable, verified experience into durable memory; retrieve a small, task-conditioned subset; preserve the evidence needed to revise or delete it.

Strongest consensus

Memory needs an explicit lifecycle—admission, representation, retrieval, revision, and forgetting—not merely persistence.

Best coding default

Repository-native instructions plus compact task state and externally verified lessons. Generated recall must not become policy.

Most common failure

Irrelevant or stale memories prime the model toward the wrong action. More recalled context can reduce task performance.

Largest open question

Who should control evolution: the same agent, a separate curator, a human reviewer, or a learned policy?

The practical test

A memory system is valuable only if it improves future decisions after accounting for capture cost, retrieval latency, prompt tokens, stale advice, privacy risk, and repair. Fast lookup is an implementation property; better behavior is the product outcome.

1No universal winner

Long context wins some factual-recall tasks; structured memory wins under budget and across sessions; procedural memory wins when outcomes repeat. Workload determines the architecture.

2Retrieval is an intervention

Every memory placed in context changes the model’s trajectory. Retrieval should be gated by expected utility and trust, not similarity alone.

3Authority must be visible

An observation, a hypothesis, a user preference, a verified procedure, and a mandatory rule are not interchangeable records.

02

Definitions

Five neighboring systems, one overloaded word

“Memory” is often used for any information outside the current message. Separating adjacent mechanisms prevents category errors.

Context
The model’s volatile working set for this inference: conversation, files, tool output, and instructions.
Compaction
A lossy summary that keeps a long-running session inside the context budget.
Checkpoint
Execution state sufficient to resume a task: plan, artifacts, cursor, pending actions.
RAG
Retrieval of an external corpus. It becomes agent memory when the corpus is formed from the agent’s history or experience.
Durable memory
History-derived state that persists and can alter behavior in a later task or conversation.

Memory is not authority

Codex and Claude Code both make this distinction in practice. Generated memories help recall; checked-in AGENTS.md/CLAUDE.md, permissions, hooks, tests, and policy control required behavior. A remembered suggestion can be wrong, stale, or omitted.

Memory is not identity

A preference such as “use terse commit messages” is scoped to a user or team. A finding such as “this service uses port 8081” is scoped to a repository and time. Treating both as an undifferentiated user profile creates leakage and contradiction.

03

Strategy landscape

Eight strategies, usually combined

These are centers of gravity, not mutually exclusive products. Mature systems compose several and assign each a different scope.

S01

Keep the transcript / use long context

Idea: avoid lossy extraction and let the model read history. Best at: exact recent evidence while it fits. Weakness: cost grows with every turn; attention and instruction adherence degrade; multi-session retention, deletion, and revision remain unsolved. A necessary baseline, not a complete memory architecture.

S02

Compact and checkpoint

Idea: summarize completed work and preserve resumption state. Best at: keeping long coding tasks moving. Weakness: summaries silently discard details and can turn tentative beliefs into facts. Claude Code compaction and MCP Memory’s fixed system/last_memory are different implementations of this family.

S03

Extract facts into a searchable store

Idea: convert interactions into small records, deduplicate/update them, then retrieve with lexical or vector search. Best at: preferences, identities, reusable facts. Weakness: extraction errors become durable; similarity is not situational relevance. Mem0 and MCP Memory occupy opposite ends of the autonomous–explicit spectrum.

S04

Build a temporal knowledge graph

Idea: represent entities, relations, episodes, and validity intervals. Best at: changing relationships and multi-hop questions. Weakness: extraction/ontology cost, graph maintenance, and another retrieval planner. Graphiti is the clearest production-oriented example.

S05

Maintain a living file/wiki

Idea: an agent curates linked, human-readable knowledge; a derived representation provides discovery or inspection. Best at: shared project knowledge, audit, and repair. Weakness: merge conflict, drift, and editorial burden—or, in database-first variants, loss of direct file repair. Karpathy’s LLM Wiki, OKF, Memento, ByteRover, and Knowledge Base Ingest explore variants.

S06

Virtualize context like an operating system

Idea: give the agent tools/policies to move state among working context, persistent blocks, archival storage, and recall. Best at: stateful agents whose memory is itself part of the control loop. Weakness: autonomous paging decisions are hard to debug. MemGPT/Letta and MemOS make this philosophy explicit.

S07

Store verified procedures and skills

Idea: distill successful trajectories into reusable code, scripts, or instructions. Best at: recurring coding and environment tasks. Weakness: a procedure is safe only when its outcome was externally checked and its preconditions remain valid. Voyager, MemP, and coding skills are exemplars.

S08

Learn the memory controller

Idea: train a policy to decide when and what to store, retrieve, compress, update, or forget. Best at: optimizing a repeated workload end to end. Weakness: training cost, distribution shift, opaque policy failures, and difficult governance. AgeMem and SWE-MeM are promising research, not settled defaults.

The key distinction

A vector database, SQLite FTS5, a graph database, and a folder of Markdown are retrieval substrates. None decides what deserves permanence, whose claim wins, when a fact expires, or whether recall helped. Those policies define the memory system.

How the lineage developed

Generative Agents made the modern pattern legible: an event stream retrieved by relevance, recency, and importance; higher-level reflections written back; plans influenced by both. Reflexion stored linguistic self-critique as episodic feedback, while MemGPT introduced explicit virtual-context tiers and Voyager turned successful behavior into executable skills. Current systems largely recombine these four ideas—stream, reflection, paging, and procedure—with stronger persistence and governance. [R3] [R5] [R4] [R6]

Deep dive

MCP Memory: a clear baseline with revealing gaps

The project from the linked HN post is valuable precisely because it is small enough to see the entire memory loop—and the missing pieces.

fellowgeek/mcp-memory

one-day implementation 12 tests passed

Audited commit 4514d1f · MIT · Python/FastMCP 3 · SQLite WAL + FTS5 · OKF v0.2 · 13 Aug 2026

What it actually does

  • Six stdio MCP tools: store, retrieve, search, delete, get-last, update-last.
  • Upserts an OKF payload under primary key (key, namespace).
  • Indexes keys, tags, and payloads with synchronized FTS5 triggers.
  • Mirrors each record to a Markdown hierarchy with index.md and log.md.
  • Uses fixed system/last_memory as an overwrite-only session checkpoint.

What it does not do

  • No automatic capture, embeddings, graph, reflection, deduplication, or consolidation.
  • No temporal ranking, stale enforcement, contradiction handling, or decay.
  • No revision history, compare-and-swap, multi-writer policy, or crash reconciliation.
  • No Markdown import/reindex, benchmark, retrieval evaluation, or client end-to-end test.
  • No guarantee that a model obeys the “call memory first” server instruction.

The write/read asymmetry

01

Agent call

Model supplies content, key, namespace, metadata, and an absolute project root.

02

Serialize

The server renders YAML-frontmatter OKF Markdown.

03

Commit DB

SQLite row and FTS trigger are committed first.

04

Mirror files

Concept file and indexes are written afterward.

05

Recall DB only

Exact retrieval and search never read or reconcile Markdown.

This means SQLite is the operational source of truth. A human edit, Git revert, or restored Markdown backup is invisible to recall. Because the database transaction precedes filesystem output, a filesystem error can split the representations. The project calls the design “dual-layer”; at this commit it is more accurately database memory with a one-way human-readable export.

Distinctive strength

OKF equips a minimal local store with explicit fields for sources, generator, verification, status, usage window, and staleness—far better raw material than an untyped vector chunk.

Retrieval trade-off

Quoted prefix-AND FTS is predictable and strong for symbols, paths, commands, and names. It misses paraphrases and returns up to ten entire OKF records, weakening its token-efficiency story.

Critical risk

Open issue #2 demonstrates ../ key traversal. Namespace and model-supplied project_root compound the path-authority problem. Logical namespaces are not security isolation.

Metadata is not policy

The schema can say stale_after: 2026-09-01, status: deprecated, or verified: …. Retrieval never interprets those fields. A stale, deprecated, unverified item ranks like a fresh reviewed one. A memory system earns its lifecycle claims only when behavior acts on the metadata.

Where it is strong

A transparent, inexpensive, local, cross-client baseline; no embedding service; good exact vocabulary; portable record format; easy to understand and extend.

Where it is weak

Extremely early; direct model writes; unsafe path resolution; passive lifecycle; token-heavy responses; dual-write inconsistency; no proof it improves agent outcomes.

Claim audit and engineering maturity
  • Supported: local persistence, FTS5 indexing, human-browseable mirrors, project/global path configuration, and plausible MCP portability.
  • Partly supported: “strict OKF compliance.” The serializer is plausible and the vendored v0.2 spec matches upstream, but the limited validator is not on the write path and reserved keys can collide with generated indexes.
  • Unproven: “sub-20ms” lookup. There is no benchmark, dataset, hardware, percentile, or comparison.
  • Tested here: all 12 tests passed under Python 3.12/FastMCP 3.0 in 0.146 seconds. The documented generic python3 path failed on Python 3.9 because the minimum Python version is undocumented.
  • Maturity signals: seven same-day commits, no release/tag, no CI, no lockfile, global warning suppression, and ordinary strings for errors.

Primary evidence: MCP tools, SQLite layer, OKF/file layer, path-traversal issue. [R15]

Deep dive

Memento: memory as governed shared knowledge

Memento is the strongest inspected example of designing authority, transactions, review, provenance, and repair before adding model cleverness.

rcarmo/memento

governance-first small-scale evidence

Audited commit 5acbf7b · MIT · Python 3.12–3.14 · Rust semantic path · Bun/Playwright UI · Git + two SQLite databases

Knowledge plane

A bare Git repository is authoritative. Concepts are validated Markdown with stable UUIDs, typed metadata, sources, supersession, and links. Every accepted write is a commit.

Control plane

control.sqlite owns proposals, reviews, idempotency, journals, leases, principals, HMAC checks, checkpoints, and access audit.

Derived plane

derived.sqlite owns FTS5, backlinks, graph metrics, optional embeddings, cache, traces, and signals. It can be rebuilt from Git.

The write contract is search → read → propose → review → apply. Application validates the entire candidate tree in a detached worktree, commits it, then compare-and-swaps the Git reference against an expected revision. A model-authored proposal cannot approve itself. This is intentionally slower than direct upsert—and much safer for shared organizational memory.

Small-model restraint

Memento once tried a broader small-model planner. Its own evidence reported 38.1% tool accuracy and 85.7% valid JSON, with no useful UNKNOWN precision. The design retreated to six shallow routing actions, strict schema validation, and abstention; deterministic code owns state transitions. This is a rare, concrete example of replacing model judgment after it failed.

Security by dataflow

Authorization filters candidates before scoring, so secret records cannot perturb visible rankings. Retrieved files, frontmatter, links, and model output are untrusted. Optional answer generation is evidence-scoped, revision-bound, citation-validated, and disabled in production without a trusted model.

Why it is distinctive

Most memory products optimize recall, then add governance. Memento begins with a state machine: proposals, revisions, identities, audit, atomic application, rollback, and rebuild. Its local model is a replaceable advisory component, not the keeper of truth.

Strengths

Human repairability; stable identity across rename; explicit conflict semantics; rebuildable indexes; provenance and rollback; pre-ranking authorization; conservative model boundary; local-first operation.

Weaknesses

Single writer; Git/worktree operational weight; current rename scan; roughly 10k-concept initial target; reader-checkout refresh is not atomic; small maintainer base and no large independent evaluation.

Release 0.3.23’s reported evidence—23 concepts, 15 synthetic queries, lexical top-5 recall 0.8333 and hybrid 0.8974—is an engineering smoke test, not a scientific comparison. A 250-concept local load test reported direct-query p50 2.435 ms, p95 81.382 ms, p99 336.447 ms. Useful, but far below production-scale proof. [R16]

Knowledge Base Ingest: memory as a provable source graph

This local project is best understood as a source-grounded semantic-memory compiler: an agent supplies judgment, while deterministic code refuses knowledge that cannot be traced to immutable evidence.

knowledge-base-ingest

provenance-first experimental v0.1

Audited local commit b26dce4 · 7 August 2026 · TypeScript/Node 20+ · Zod · better-sqlite3/FTS5 · Claude Code skills · no license declaration found

Category boundary

This is not autobiographical agent memory. It does not remember conversations, preferences, task checkpoints, or successful trajectories, and it is not automatically injected into a new chat. It compiles a finite source corpus into external semantic and organizational memory: claims, a synthesis hierarchy, entities, relationships, conflicts, open questions, and the evidence behind them.

The compilation pipeline

01

Preserve

Hash the original bytes; store an immutable, content-addressed source and versioned canonical text.

02

Index

Deterministically tile text into structure-aware chunks and synchronize FTS5 through SQL triggers.

03

Propose

The coding agent submits typed JSON for the hierarchy, claims, relationships, and synthesis.

04

Prove

Zod, exact unique-quote resolution, scope checks, and one immediate transaction accept or reject the batch.

05

Project

Queries return claims plus quotes; a deterministic Markdown tree renders the human view and exposes drift.

Evidence plane

Original files, canonical text, chunks, and exact spans are separate from model-authored interpretation. A span stores absolute offsets and a quote hash; the CLI derives both.

Knowledge plane

SQLite is authoritative for claims, claim–span edges, the arbitrary-depth synthesis tree, graph relationships, currentness, reviews, and change records.

Projection plane

kb/ is a deterministic read-only render with claim footnotes. Humans can inspect it, but edits are overwritten; render --check detects divergence.

The normal claim path is deliberately fail-closed. The agent supplies a chunk ID and quotation; code must find that quote exactly once inside the chunk, derive absolute UTF-16 offsets, recheck the canonical text, validate all citations, then persist the entire batch or none of it. Sources and natural keys are content-derived; mutations use BEGIN IMMEDIATE; dry runs can be bound to an expected payload digest; synthesis writes require the previously read body hash. The database enables foreign keys, strict tables, WAL, a five-second busy timeout, and pre-migration backups.

Most distinctive mechanism: review that expires correctly

Coverage exceptions, possible-duplicate coexistence decisions, and relationship reviews are immutable records bound to a fingerprint of the exact subject being reviewed. If the evidence or subject changes, the old acceptance no longer matches and the question reopens. Likewise, “source finalized” is not a permanent done bit: readiness is recomputed across integrity, extraction, judgment, and synthesis. This is materially stronger than a passive verified: true field.

Strengths
  • Structural provenance: fabricated quotations and dangling evidence cannot pass normal claim or relationship writes.
  • Clean division of labor: the model chooses and interprets; code owns hashing, schemas, offsets, transactions, staleness, drift, and verification.
  • Evidence survives synthesis: claims, conflicts, superseded sources, and exact spans remain inspectable when prose is regenerated.
  • Currentness is active: source/claim supersession, conflicted status, recursive stale-node propagation, successor lookup, and fingerprinted reviews affect workflow behavior.
  • Safe local writes: atomic batches, idempotent IDs, dry runs, optimistic hashes, path containment, FTS triggers, and source-file race handling reduce agent-caused corruption.
  • Agent-readable interface: generated help, typed issue codes, bounded results, continuation actions, and uniform JSON envelopes reduce prompt bookkeeping.
  • Small infrastructure: no hosted model, embedding API, graph server, or vector database is required.
Weaknesses
  • A quotation is not entailment: a real sentence can still be summarized incorrectly. answer-check verifies citation structure and current status, not meaning.
  • Formation is expensive: the agent must inspect chunks, author claims/graph payloads, adjudicate candidates, synthesize bottom-up, and clear finalization gates.
  • Recall is lexical: BM25/FTS5 is strong for identifiers but misses paraphrase; the graph is not traversed or ranked during retrieval.
  • The database is irreplaceable: Markdown cannot rebuild the KB, raw sources cannot reconstruct model judgments, and the changelog is not a replayable event log.
  • Single-user and local: no API/MCP transport, authenticated identity, curator separation, RBAC, encryption, remote sync, or distributed write protocol.
  • Security stops short of trust: source paths are contained, but there is no quarantine, source-trust class, instruction/data separation, or prompt-injection policy.
  • No forgetting policy: supersession preserves history; there is no retention, expiry, privacy erasure, or access-sensitive recall lifecycle.
  • Input and ontology limits: binary documents need a sidecar transcription; entity matching is exact/lightly normalized; graph vocabulary is advisory.
Two provenance exceptions matter

First, exact evidence proves that a quote exists, not that a model-authored claim is a fair implication. Second, entity descriptions are not span-backed: they record a first-seen source but can contain agent-authored prose without an exact quotation. The broad slogan “every generated part traces to a source” is therefore directionally right for claims, relationships, and cited synthesis, but too strong for every rendered statement. The current verifier also rechecks spans against canonical database text, not the entire stored original against its raw hash; tampering outside cited regions can escape that audit.

Evidence and maturity

In a fresh isolated clone of this commit, all 987 tests across 91 files passed; strict type-checking also passed. The checked-in paired skill evaluation ran six isolated agent sessions—old versus revised skills over creation, ingestion, and query—and all reached their terminal correctness gates; revised skills reduced payload retries from two to zero while invocation counts were effectively flat. A separate two-source CLI evaluation exercised supersession, coverage, quote provenance, strict verification, and render drift. These are unusually strong product-level mechanics tests, not an independent memory benchmark.

Observed retrieval limits

The project’s own evaluation found that claim-type-filtered ask-context under-returned for category questions and needed a node fallback. It also found that structural answer checking can reject a harmless framing sentence. The retrieval fixture is eight queries, so there is no evidence yet for large-corpus recall, semantic robustness, latency distribution, or improved downstream coding outcomes.

Bottom line: this is one of the strongest inspected demonstrations of P02, preserve evidence separately from synthesis, P05, compute currentness from evidence and review, and P09, keep the model advisory where code can decide. It makes P07’s canonical/derived boundary unusually clear, but not yet its recoverability promise because the database cannot be rebuilt from sources and Markdown. It is best for technical or research knowledge whose claims must be auditable. It should complement—not replace—a coding agent’s working context, checkpoints, repository instructions, procedural skills, or personal cross-chat memory. [R34]

08

Other architectures

What the major project families teach

Each project makes one or two architectural bets unusually clear. Their lessons are more useful than a winner-take-all ranking.

Letta / MemGPT

OS metaphor

Core blocks remain in prompt; archival passages live behind vector search; raw messages remain in recall memory. The agent pages information through tools, making memory part of its control loop. This is the foundational “virtual context” design. Letta’s legacy V1 server persists agents, blocks, histories, messages, passages, and archives in SQL.

Lesson: a hot/cold hierarchy is powerful, but autonomous paging and self-editing make errors difficult to observe. [R4]

Letta Code

agent-owned files

Current Letta moves coding memory into a Git-backed filesystem. Small system/ files compile into the prompt; larger reference files stay detached. Reflection/history subagents use worktrees; /sleeptime consolidates offline and /doctor reorganizes.

Lesson: file ownership, history, and offline reflection fit coding well. Treating memory as agent identity can also turn uncertain inference into persistent behavioral bias. [R19]

Mem0 OSS v3

fact extraction

One LLM pass extracts additive facts, embeds them, and scopes them by user, agent, or run. Search fuses vectors, provider keyword/BM25, entity overlap, and optional reranking. Unlike the older paper algorithm, current OSS v3 does not automatically update/delete earlier facts; contradictions accumulate as history.

Lesson: a tiny API wins adoption, but paper, hosted platform, and current OSS behavior must be separated. ADD-only lowers write latency while moving contradiction resolution downstream. [R20]

Graphiti

bi-temporal graph

Episodes preserve source evidence; entity nodes evolve; fact edges carry valid, invalid, expired, created, and reference times. Ingestion resolves entities, detects contradictions, and invalidates old edges without erasing them. Search combines embeddings, full text, traversal, RRF/MMR/cross-encoder options.

Lesson: time and provenance deserve first-class representation when relationships change. The cost is multiple extraction calls, entity-resolution error, and graph operations. [R21]

LangMem

toolkit

LangMem cleanly separates semantic facts/profiles, episodic examples, and procedural prompt optimization. Managers can insert/update/delete structured schemas in the hot path or via background reflection; persistence is delegated to LangGraph’s cross-thread store rather than its thread checkpointer.

Lesson: foreground versus background writing is a real freshness/latency trade-off. A taxonomy and primitives are not a governance layer. [R22]

ByteRover

coding Context Tree

Knowledge lives under .brv/context-tree in typed <bv-topic> HTML, organized hierarchically and searched with MiniSearch, paths, relations, and lifecycle signals. Native execution has five tiers from cache to agentic retrieval; external MCP/tool mode intentionally uses only deterministic tiers 0–2 and leaves synthesis to the caller.

Lesson: progressive retrieval, OOD abstention, review, and lossless archive are compelling. Inspect source: the paper’s Markdown format, title boost, thresholds, shared lifecycle state, and five-tier common path do not all match shipping code. Elastic-2.0 is source-available, not OSI open source. [R23]

Karpathy’s LLM Wiki + OKF

file-first idea

The LLM Wiki proposal places an agent-maintained linked Markdown layer between immutable raw sources and users, with content indexes, chronological logs, Git history, linting, and optional hybrid search later. Google’s OKF supplies a portable frontmatter vocabulary for type, source, generator, verification, lifecycle, and attested computation.

Lesson: human-readable source plus rebuildable retrieval is an excellent default. “Near-zero” LLM bookkeeping cost and autonomous editorial quality at large scale remain hypotheses. [R17] [R18]

Cognee · MemOS · A-MEM

research frontier

Cognee offers broad graph/vector/ontology pipelines and coding hooks. MemOS spans textual, KV-cache/activation, and LoRA/parametric memories in MemCubes. A-MEM grows a Zettelkasten-like network by having an LLM link and rewrite nearby vector-retrieved notes.

Lesson: these broaden the design space, but breadth is not maturity. Current evidence is mostly project-authored; A-MEM in particular lacks production durability, concurrency, provenance, and governance. [R24]

Coding products

Codex and Claude Code: similar layers, different control

Both separate durable instructions from generated recall. Codex emphasizes asynchronous extraction/consolidation and provenance; Claude Code emphasizes direct, editable Markdown and a compact per-repository index.

Reflection from inside this Codex run

This report exercised three distinct mechanisms. The live conversation and tool outputs were working context. When that context became large, a continuity summary preserved the research goal, source map, delegated work, and remaining tasks—but not every raw passage; details sometimes had to be reopened. That is lossy same-task compaction. Cross-conversation Codex Memories are a separate, optional background system, and the user-supplied AGENTS.md is a third mechanism: explicit authority. Treating these as one “memory” would obscure their different guarantees.

Codex Memories

off by default

Eligible completed root sessions are processed asynchronously in two phases. Phase 1 extracts a raw memory and rollout summary using strict structured output after filtering developer messages, reasoning, compaction artifacts, injected instructions, and skill fragments; inputs and outputs are secret-redacted. Phase 2 selects bounded candidates and gives a dedicated consolidation agent a restricted memory workspace.

The generated state is local under ~/.codex/memories/ and separate from ChatGPT web memory. Per-chat controls independently govern whether a conversation may use memory and whether it may contribute to future memory.

The consolidator is ephemeral and cannot use memories, apps, MCP, plugins, collaboration, approvals, or the network. Generated Markdown preserves source thread, time, rollout path, working directory, and Git branch. A small memory_summary.md is injected with a 2,500-token cap; the read path then searches MEMORY.md and opens at most one or two relevant rollout summaries or skills.

Retrieval is bounded lexical search, not embeddings. Path access rejects roots, traversal, hidden components, prefix escape, and symlinks. Direct “remember this” requests become validated timestamped notes, and stored content is framed as information—not trusted actions.

Claude Code memory

auto memory on

Claude Code starts each session fresh, then layers human-authored CLAUDE.md guidance and agent-authored auto memory. Instructions can be managed, user, project, or local; nested files load as the agent enters directories, and @ imports compose guidance.

Auto memory is machine-local under ~/.claude/projects/<project>/memory/ and shared by worktrees of the same repository. A concise MEMORY.md index is loaded every session—up to the first 200 lines or 25 KiB—and topic files are read on demand. Files are plain Markdown, visible, editable, and deletable through normal tools or /memory.

Compaction is separate: it clears older tool output and summarizes conversation state. Root project guidance survives, while conversation-only instructions can be lost. Claude’s docs likewise describe memory as context, not enforcement; permissions, hooks, and checked-in rules own hard constraints.

The compact summary still primes every opted-in chat, and public evidence does not yet establish its task-level benefit, false-memory rate, or long-term repair quality.

Coding-agent focus

What should a coding agent remember?

Coding work has unusually strong external truth: the repository, compiler, tests, issue tracker, deployment, and runtime. A good memory architecture exploits that instead of building a shadow codebase.

1 · Invariants

Build/test commands, policy, architecture boundaries, safety rules. Home: checked-in AGENTS.md, ADRs, schemas, tests, hooks. Reviewed; authoritative.

2 · Task state

Goal, plan, changed files, failing check, next step. Home: live context + resumable checkpoint. Short-lived; replaceable.

3 · Project model

Symbol map, ownership, subsystem relationships, operational facts. Home: generated index/wiki with source links, revision, and freshness.

4 · Verified experience

Failure pattern, successful repair, reusable procedure, environment quirk. Home: evidence-linked episode or skill with test verdict and preconditions.

Do not copy the repository into memory

Code facts change too quickly. Store navigation cues, decisions, and verified lessons; resolve current symbols, APIs, tests, and configuration from the checked-out revision. This boundary was the strongest point of agreement in the HN discussion and is explicitly reinforced in Codex’s read-path instructions.

Competing philosophies

The disagreements are about control and truth

Storage debates are proxies for deeper questions: who may write, what can be forgotten, whether history is rewritten, and whether memory is an instrument or part of the agent’s identity.

Rewrite or preserve contradictions?

Mem0 v3 is predominantly additive: keep both facts and resolve later. Graphiti invalidates old facts while preserving their temporal history. Letta/ByteRover consolidate or reorganize. Add-only maximizes evidence but accumulates noise; rewrite keeps prompts clean but can erase nuance. The robust middle is append + supersede: immutable evidence, an explicit current view, and reversible consolidation.

Files or a service?

Files/Git optimize ownership, diff, backup, and universal coding-agent access. A service optimizes cross-device availability, authorization, concurrency, and clients without a filesystem. The strongest hybrid makes a durable format canonical or exportable, gives API writes revisions/idempotency, and treats indexes as rebuildable.

Synthesis

The philosophies need not collapse into one. Personal coding memory can be agent-edited files; shared operational knowledge can require Memento-like review; high-value corpus claims can use Knowledge Base Ingest’s evidence compiler; time-varying customer facts can use a Graphiti-like model; high-volume personalization can use Mem0-like extraction. The unifying contract is typed authority, evidence, scope, revision, and bounded recall.

Inferred principles

Ten principles for building memory that ages well

These principles recur in successful systems, are supported by negative results, or fall directly out of the security and lifecycle constraints.

P01

Type memory by function, scope, and authority

Working state, semantic fact, episode, procedure, preference, and prospective intention need different retention and retrieval. Include user/repo/team scope and classify the claim as observation, inference, reviewed knowledge, or policy. This prevents an anecdote from silently becoming a command.

P02

Preserve evidence separately from synthesis

Keep immutable source turns, logs, files, test runs, and timestamps behind every distilled memory. A summary is a view, not the raw event. Provenance enables revalidation, explanation, deletion, and re-consolidation with a better model.

P03

Make admission stricter than retrieval

Persistence amplifies mistakes and prompt injection across time. Before writing, evaluate reuse, novelty, confidence, trust origin, scope, sensitivity, and conflict. Untrusted web/tool output should enter quarantine or evidence storage—not developer-level prompt memory.

P04

Use progressive, task-conditioned retrieval

Start with a tiny index or candidate outline; use exact identifiers/path/lexical matching first; add semantic or graph expansion when the query demands it; fetch full records last. Let task phase and expected action gate recall. Return omission handles, not ten full documents.

P05

Represent time and contradiction explicitly

Record observed time, effective validity, source revision, expiration/review date, and supersession. Avoid destructive overwrite. “Current” should be a computed view over evidence and review—not the most recent model completion.

P06

Ground procedural memory in outcomes

A model’s explanation of why a patch worked is not a verdict. Promote procedures only when tests, compiler, runtime, simulator, benchmark, or human review establish the result. Store preconditions and failure signatures alongside the steps.

P07

Separate canonical, control, and derived state

Canonical content must be inspectable/exportable and recoverable. Journals, leases, authorization, and idempotency belong in control state. FTS/vector/graph indexes and caches should be rebuildable. Declare the authority and reconciliation rule for every duplicate representation.

P08

Apply identity and authorization before ranking

Resolve project/user/tenant on the server; never accept arbitrary model-chosen paths as identity. Filter inaccessible candidates before scoring so secret material cannot influence visible rankings. Protect shared writes with expected revision, idempotency, or immutable events.

P09

Keep models advisory at state boundaries

Models are excellent at extraction, classification, synthesis, and proposing links. Deterministic code should validate schemas, paths, revisions, state transitions, retention, permissions, and tool budgets. High-impact or shared memories need review.

P10

Design for inspection, deletion, and evaluation

Users need view/edit/delete/export/disable controls and clear use-versus-contribute settings. Operators need traces from source → memory → retrieval → action → outcome. Evaluate task quality, abstention, revision, privacy, cost, and latency against no-memory and full-context baselines.

Evidence verdict

Accepted, rejected as defaults, and unresolved

“Flawed” here means repeated empirical failure or a known structural defect in the naive form—not that no carefully bounded variant can ever work.

Strong convergence

  • Small hot context + searchable cold memory
  • Explicit scope and memory type
  • Evidence/provenance behind synthesis
  • Progressive, bounded retrieval
  • Temporal revision and rollback
  • Exact + semantic retrieval where needed
  • External verification of procedures
  • User visibility, deletion, and export
  • End-task and lifecycle evaluation

Rejected as defaults

  • Load all accumulated memory every session
  • Embed everything + nearest neighbor = memory
  • Similarity = truth, importance, or relevance
  • Model self-report = successful experience
  • Shadow copy of a changing codebase
  • One irreversible summary of raw history
  • Passive stale_after metadata = freshness
  • Dual writes without canonical authority/reconciliation
  • Agent-chosen filesystem path = safe namespace

Still unresolved

  • Agent self-curation vs separate extractor
  • Files vs temporal graph at real scale
  • Optimal decay and forgetting policy
  • Autonomous reflection/dream quality
  • Identity/persona memory’s net value
  • Learned controllers outside training distribution
  • Parametric/KV persistent memory portability
  • Git vs API/ETag under many writers
  • A trustworthy universal benchmark
A qualified verdict on long context

Long context is not “disproven.” It is often the strongest baseline for factual recall while the complete evidence fits, and recent work reports GPT-5-mini full context outperforming memory systems on some benchmarks. It does not solve persistent cross-session state, privacy/erasure, cost growth, temporal revision, or prospective action. Benchmark it; do not confuse it with a lifecycle. [R33]

Reference architecture

A trust-aware memory stack for coding agents

This design composes the strongest ideas from the inspected systems while keeping the common case file-native and small.

L0 · Authority

Repo truth

Code, tests, ADRs, AGENTS, policy, issue state. Live and versioned. Memory may point here, never override it.

L1 · Working

Task state

Context, plan, scratch, resumable checkpoint. Compact aggressively; expire at task completion.

L2 · Project

Semantic map

Generated navigation, components, owners, commands. Source-linked and revision-aware; rebuildable.

L3 · Experience

Verified episodes

Problem, conditions, action, evidence, verdict. Retrieved by task phase and failure signature.

L4 · Procedure

Skills

Reviewed scripts/playbooks with preconditions and checks. Versioned; shared only through approval.

Write path

  1. Capture immutable evidence with origin, scope, time, and revision.
  2. Classify candidate kind and sensitivity; reject secrets and low-reuse detail.
  3. Check novelty, contradiction, and existing supersession chain.
  4. Generate a proposal; deterministic validators enforce schema/path/access.
  5. Require external verdict for episodes and human review for shared/high-impact records.
  6. Commit canonical content and journal atomically; update derived indexes afterward.

Read path

  1. Resolve user, repository, revision, task phase, and allowed scopes.
  2. Search cheap exact/path/lexical indexes; add vector/graph expansion only as needed.
  3. Gate candidates by trust, validity, task utility, and contradiction—not score alone.
  4. Return a short outline with source, age, confidence, and handles.
  5. Open one or two full records; verify drift-prone claims against L0 authority.
  6. Log influence and outcome so use can trigger review—not blindly boost “importance.”

Minimum durable record

id: stable opaque identifier
kind: semantic | episode | procedure | preference | intention
scope: user | repo@revision | team | organization
authority: observed | inferred | verified | reviewed | policy
claim: concise statement or procedure reference
evidence: immutable source handles + quoted region hashes
time: observed_at, valid_from, valid_to, review_after
lineage: generated_by, supersedes, derived_from
verdict: verifier, outcome, environment, confidence
access: owner, readers, sensitivity, retention/delete state
YAGNI path

Start with checked-in instructions, a bounded checkpoint, atomic evidence-linked Markdown, Git history, and lexical search. Add embeddings only after paraphrase failures are measured; add a graph only after temporal/multi-hop failures are measured; add autonomous consolidation only after manual curation becomes the bottleneck.

A minimum evaluation protocol

1 · Baselines

Compare no memory, full available history, a concise human note, and the proposed system. Keep agent model, tool harness, token budget, and repository revision fixed.

2 · Lifecycle

Measure capture precision, recall@budget, contradiction revision, temporal validity, abstention, deletion completeness, and recovery from corrupt/poisoned state.

3 · Outcomes

Track task success, repeated failure, steps, wall time, model/tool tokens, write cost, latency percentiles, and human repair effort across many future tasks.

Leaderboard caution

An independent, reproducible 2026 audit of LoCoMo reports 99 errors among 1,540 gold answers (6.4%) and a judge accepting 62.81% of intentionally wrong vague answers, alongside inconsistent token/call accounting and omitted categories. It is not peer-reviewed and does not invalidate every LoCoMo experiment; it does invalidate treating small vendor score differences as settled fact. Cross-paper tables with different backbones, prompts, judges, and product versions are not rankings. [R32]

Persistent memory creates persistent attack surface

Recent “Zombie Agents,” sleeper-memory, and memory-poisoning studies demonstrate the core threat: a one-time indirect prompt injection can be distilled into long-lived state and reactivated in later clean conversations. Repeated consolidation can strengthen the malicious instruction. Session-level input filters are therefore insufficient; security must cover admission, storage, retrieval, action, and repair. [R14]

Memory threats persist across sessions, so controls must cover the full lifecycle.

Privacy architecture

Prefer local storage for personal memory, redact secrets before extraction, minimize retained raw text, separate billing/organization identities, and make “may use” independent from “may contribute.” For sensitive domains, keep identifiers inside a trusted boundary and hydrate only the minimum purpose-specific context on return.
